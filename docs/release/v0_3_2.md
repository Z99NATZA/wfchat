# v0.3.2 - Production Chat And Session Hardening

Release date: 2026-08-05

This patch release extends the production security boundaries introduced in
v0.3.1 and fixes OpenAI chat compatibility for `gpt-5.5`.

## Security And Session Lifecycle

- Guest-session admission is limited to 10 requests per resolved IP and 60
  requests globally per API process each minute.
- `/api/auth/guest` and the session-creation path of `/api/auth/me` are the only
  unauthenticated guest-admission paths. Profile, follow-up, learned-context,
  sync, and Cafe handlers require an existing active session instead of
  creating one implicitly.
- Logout atomically revokes an active registered or admin session and issues one
  replacement guest session. Missing, invalid, revoked, and guest sessions
  cannot mint replacements.
- Each runtime cleanup pass re-parents at most 1,000 legacy guest candidates,
  then deletes at most 1,000 expired or revoked guest sessions. Cleanup runs
  every 10 minutes; ambiguous or incomplete account mappings are retained.
- The nginx web server sends a Content Security Policy, denies frame embedding,
  and enables content-type and referrer protections.

## Chat Limits And Consistency

- Production admits at most 50 chats per owner, 100 stored messages per chat,
  and 500,000 stored Unicode scalar values per chat. The database transaction
  rechecks each storage limit before committing.
- Chat creation and message sends share limits of 20 requests per session and
  resolved IP and 120 globally per API process each minute. Chat generation and
  message clearing share one exclusive permit per chat so a clear cannot race
  an in-progress append.
- Chat lists return bounded summaries with a truncated last-message preview.
  Successful sends return only the newly committed user and assistant pair.
- Authenticated chat and follow-up responses use private, no-store caching.

## Provider Compatibility

- OpenAI chat requests use `max_completion_tokens` for `gpt-5.5` and its
  variants while preserving `max_tokens` for existing compatible models.

## Upgrade Notes

- The API applies the guest cleanup and legacy promoted-session migrations at
  startup. Existing registered sessions and account-owned data are retained.
- The initial legacy promoted-session migration may process all eligible legacy
  guest candidates in one startup transaction. Runtime re-parenting and
  deletion are each bounded to 1,000 sessions per pass after migration.
- Production deployments that override `CHAT_GLOBAL_REQUESTS_PER_MINUTE` must
  use a value of 120 or lower before upgrading. Values above 120 fail production
  startup validation; v0.3.1 allowed values up to 6,000.
- No new environment variable is required. The new guest-admission, chat-rate,
  and chat-storage limits have defaults documented in `apps/api/.env.example`.
- Rate, admission, and concurrency limits are process-local and reset when the
  API process restarts.
