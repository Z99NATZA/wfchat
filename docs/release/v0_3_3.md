# v0.3.3 - Chat Image Attachment Storage Hardening

Release date: 2026-08-06

This patch release prevents leaked chat image files, reclaims orphaned files,
and limits stored images to 200 MiB per owner.

## Image Validation And Uploads

- New uploads accept PNG, JPEG/JPG, and WebP only. The API detects the format
  from file bytes, validates dimensions and decoder allocation, and fully
  decodes the image before accepting it.
- Upload buffering is bounded by the configured image limit plus fixed
  multipart overhead. Decode concurrency is fail-fast and returns `429` when
  the per-process capacity is occupied.
- Failed uploads no longer leave untracked final-path files. Their cleanup uses
  the same durable deletion lifecycle as every other attachment-removal path.
- Attachment previews remain owner-protected and use backend URLs. Historical
  linked attachments remain previewable when their stored format is no longer
  accepted for new messages.

## Durable Deletion And Reclamation

- Hard deletion of attachment metadata now creates a durable file-deletion
  record in the same PostgreSQL transaction, including deletions caused by chat,
  message, or guest-session cascades.
- The API processes deletion records at startup and hourly with bounded,
  retryable work. Missing files count as successful idempotent deletion.
- Bounded attachment-directory reconciliation enqueues eligible unreferenced
  image files for the same deletion worker.
- Deletion ownership survives guest-session cleanup and follows guest-to-user
  promotion.

## Per-Owner Storage Quota

- `CHAT_ATTACHMENT_MAX_STORAGE_BYTES_PER_OWNER` defaults to 209,715,200 bytes
  (200 MiB), must be positive, and cannot exceed that value in production.
- Registered sessions share quota by user id; guest sessions have independent
  quotas. Quota admission is atomic per owner across concurrent uploads and API
  replicas.
- Live pending and linked attachments count toward usage. Durable deletion
  records remain chargeable until physical deletion is confirmed.
- An upload that would exceed quota returns `409 Conflict` with
  `{"error":"conflict: image attachment storage quota exceeded"}` before
  writing the final-path file or leaving attachment metadata behind.

## Upgrade Notes

- The API applies the durable deletion migration automatically at startup and
  moves existing soft-deleted attachment metadata into the deletion queue.
- Multi-replica deployments with image upload enabled must mount the same
  persistent `CHAT_ATTACHMENT_UPLOAD_DIR` on every API replica.
- Add `CHAT_ATTACHMENT_MAX_STORAGE_BYTES_PER_OWNER` to explicit environment
  configuration when a value below the 200 MiB default is required.
